PRIMARY GOAL
Build a production-minded, installable, open-source WordPress security auditing plugin. It must run real, read-only checks and produce evidence-based findings, not a simulated dashboard. The plugin must be capable of functioning locally without any external provider. Optional vulnerability lookups and WordPress.org core checksum retrieval require explicit, separate administrator opt-ins.

NON-NEGOTIABLE REQUIREMENTS
- Follow SPEC.md and DESIGN.md. Do not silently shrink scope or replace a security audit with fake data.
- Never implement automated fixes, password inspection, malware claims, exploitation, port scans, unauthorised scanning or arbitrary URL requests.
- Secure every private REST endpoint with a real permission_callback using manage_options. Use WordPress authentication/nonces for browser state changes. Nonces never replace capability checks.
- Treat external provider output as untrusted. Validate schema, strip unsafe HTML, constrain URLs, cap sizes/timeouts, cache appropriately and fail safely to unknown.
- No network calls by this plugin before opt-in. No telemetry, external fonts, remotely loaded JavaScript, hidden services or unnecessary SaaS.
- Never include secrets, absolute server paths or sensitive configuration content in findings, API output, logs or report exports.
- If an operation cannot be evaluated, show unknown. Never present unavailable data as a passed security check.
- Scans must use bounded background batches, safe locks, idempotent retries and a secure fallback for sites where WP-Cron is delayed.
- Use a genuine WordPress plugin backend, not a separate Node service or mock website. Build a polished React/TypeScript admin interface with WordPress-native dependencies and scoped CSS.
- Include unit, integration and E2E tests, a clean installable plugin ZIP and development/release documentation.
- Avoid claims that a passing audit guarantees security or that this plugin has been accepted by WordPress.org.
